# Publicación autónoma del complemento privado — procedimiento operativo (23/11/2026)

**Regla de servicio al usuario:** NO pedirle que descargue, copie, transporte ni adjunte archivos ZIP por defecto. El ejecutor debe agotar las vías autorizadas de transferencia y publicación que ya funcionaron. No declarar un bloqueo por la mera existencia del ZIP en Debian o por fallar `git push` sin credenciales.

## Evidencia de éxito reproducible

El 23/11/2026 se actualizó desde la conversación **el plugin privado personal existente** `plugins_6add39166308819193bc271cfa0af302`, de 0.4.53 a **0.4.54**, release `pluginrel_6b039337d3d4819195f873bcdb030bc2`, sin intervención del titular en archivos. GitHub `vtsalamanca/gestor-de-skills`, commit `ca0251e517998dcc19fb004264334b6d1de78d1e`. Se compararon los siete archivos distribuidos con GitHub **byte a byte**: siete coincidencias; Plugin Creator informó 88 archivos, ámbito USER, visibilidad PRIVATE. Pruebas previas en Debian: 11 del empaquetador y 64 del comparador. El Bibliotecario registró revisión 28. La skill cargada en el chat anterior siguió siendo 0.3.6 (caché): no confundir instalación con recarga de la sesión.

**Qué hizo posible la publicación:** crear un archivo real en el entorno de artefactos de la conversación (no solo en `/home/labgestor`), obtener su **identificador de archivo subido al host**, y proporcionar ese ID a `Plugin_Creator.update_plugin(archive=..., expected_release_id=...)`. Un ensayo previo con ZIP deliberadamente inválido fue rechazado sin mutar la release; el paquete correcto fue aceptado. El nombre del archivo, una ruta Debian, la salida base64 y un URL de GitHub NO son por sí solos el identificador admitido. La carga de archivos del host debe estar realmente disponible en la sesión; no presumir que lo estará en todas.

## Secuencia preferente en futuros cambios (sin pasos manuales)

1. **Comprobar disponibilidad y autorización:** recuperar esta guía, las herramientas activas `Control Debian`, `GitHub`, `Plugin Creator` y el constructor local de artefactos; comprobar 0 € de coste incremental. Para catalogación, resguardo y publicación de habilidades pedir autorización específica **solo si no se concedió ya para el lote**. Una autorización anterior no habilita automáticamente nuevos lotes.
2. **Identidad y preflight:** recuperar `plugin_id`, `current_release_id`, USER/PRIVATE; revisar Git `main` y cambios locales ajenos. No usar Desktop Commander si Control Debian permite hacerlo. No crear un plugin nuevo ni publicar a otro destino.
3. **Código y pruebas:** actualizar solo los archivos relevantes y las versiones de ambos manifiestos; usar GitHub como fuente canónica, Debian como checkout de trabajo. Pasar pruebas, empaquetar desde SHA inmutable con `scripts/package_plugin.py`; verificar estructura, versiones, ausencia de secretos, número de skills, SHA-256 e inventario. Guardar rollback.
4. **Publicar GitHub aun sin credenciales HTTPS en Debian:** si falla `git push --dry-run`, usar el **conector GitHub** (`create_blob`, `create_tree`, `create_commit`, `update_ref` con SHA esperado y sin force), verificando hashes de blobs y árbol con los de `git` local. Después `git fetch` y reconciliar checkout conservando cambios ajenos. No atribuir el fallo de credenciales al plugin.
5. **Llevar los bytes al publicador, SIN molestar al usuario:** preferir archivo ZIP generado en el runtime de artefactos de esta conversación desde el commit canónico y cargado al host, recibiendo un **file ID** válido. También está disponible en el repositorio el puente `.github/workflows/prueba-puente-plugin.yml` (runner estándar de repositorio público, paquete ZIP intacto, retención 1 día); comprobar estado de la ejecución, `fetch_workflow_run_artifacts` y `download_workflow_artifact` como alternativa, **verificando** que la referencia retornada sea transferible a Plugin Creator antes de usarla. Si se reconstruye desde Debian, cotejar su SHA-256 y no volcar secretos ni usar alojamiento público externo. No enviar texto base64 ni rutas inventadas como `archive`.
6. **Publicar una sola vez:** releer `current_release_id` inmediatamente antes; `update_plugin` sobre el ID existente con ZIP/tar.gz host-uploaded realmente accesible y `expected_release_id` vigente. Si da error tras el intento, consultar el estado antes de reintentar; nunca arriesgar doble publicación.
7. **Postflight obligatorio:** consultar `get_plugin_metadata` y `get_plugin_files`, confirmar nueva release, versión, USER/PRIVATE, archivos añadidos y todos los cambios **comparando contenido** con GitHub. Verificar versión anterior conservada para rollback; registrar hito en Bibliotecario con operación idempotente y relectura. Carga de un chat nuevo o cliente Codex solo se declara validada si se comprueba aparte.

## Escalada y límites

- **Nunca** ofrecer como primer paso «adjúntame el ZIP». Antes probar generación local de artefactos, puente de GitHub Actions y mecanismo de carga del host, con una comprobación acotada por hipótesis.
- Si faltan herramientas de carga en ese entorno, explicar la **frontera exacta** con evidencias; solo entonces pedir la mínima intervención indispensable. No anunciar imposibilidad general de algo ya conseguido.
- Nada de APIs o runners facturables, claves, cookies, perfiles de navegador o datos personales en ZIP, GitHub, logs ni chats. No efectuar publicación que no esté autorizada para ese lote.
- Estados separados: `CODIGO_OK`, `GITHUB_OK`, `PAQUETE_OK`, `TRANSFERENCIA_OK`, `PLUGIN_OK`, `CARGA_NUEVO_CHAT_NO_PROBADA`. No cerrar como instalado cuando solo existe en Debian o GitHub.

**Resumen imperativo:** «Si puedo publicar desde el laboratorio y el host de ChatGPT, lo hago yo; no convierto la transferencia de un ZIP en una tarea para el usuario».
